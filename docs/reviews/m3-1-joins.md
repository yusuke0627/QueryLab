# M3-1 明示的なJOINのレビュー

## ゴールと読み順

「注文に対応する商品を一緒に表示する」のような検索を、結合先と条件を指定して組み立てます。
[モデル](../../model.go) → [検証](../../validate.go) → [SQL生成](../../dialect/sqlite/compile.go)
→ [Go生成](../../gogen/generate.go) → [実SQLiteテスト](../../execution/join_test.go)の順で読めます。

たとえば、`Select.Joins` に次の要素を入れます。左の `orders` は `From` で別名 `o` を指定済みです。

```go
q.Join{
    Kind:  q.LeftJoin,
    Table: q.Table{Name: "items", Alias: "i"},
    On:    q.Eq(q.Ref("o", "id"), q.Ref("i", "order_id")),
}
```

`q.Ref("o", "id")` は「別名 `o` の `id` 列」です。`Eq` はここでは値を比較せず、
SQLiteに渡す「二つの列が等しい」という式のデータを作ります。

## 判断と処理の流れ

外部キーによる自動結合ではなく、結合の種類・右側のテーブル・ON条件をモデルに保存します。
同じ外部キーでも、何を表示するか、対応する行がない注文を残すかは検索ごとに異なるためです。

1. `FROM` と各 `JOIN` の名前を順番に登録します。別名があるときは別名を使います。
2. 各 `ON` はその時点までに登録された名前だけ参照できます。SELECT・WHERE・ORDER BYは全体を参照できます。
3. 同じ名前の重複はASCIIの大文字・小文字を区別せず拒否します。自己結合には別々の別名を使います。
4. SQLは結合順を維持し、値は `?` と引数に分けます。引数の順はSELECT → ON → WHERE → ORDER BY → LIMIT → OFFSETです。
5. Go生成とJSON保存でも結合順と条件を維持します。SQLとGoの生成は同じ検証を通ります。

名前登録と式の確認は、名前の文字数を含め入力の大きさに対しておおむね線形です。
実際にSQLiteが結合を実行する時間や行数は別で、データ量や索引、条件に依存します。性能測定はしていません。

## 行数・NULL・集計

注文1に商品が2件あり、注文2に商品がないとします。

| 結合 | 返る行 |
| --- | --- |
| INNER JOIN | 注文1と商品A、注文1と商品B |
| LEFT JOIN | 上の2行に加え、注文2とNULL |

右側の商品名を絞る条件をONに置くと、合う商品がない左の注文も残ります。
同じ条件をWHEREに置くと、結合後のNULL行も除かれます。[SQLite公式のSELECT仕様](https://www.sqlite.org/lang_select.html#whereclause)も参照してください。

この例で結合後に `COUNT(*)` を使うと、数えるのは注文そのものではなく結合後の行です。
注文の件数を数えたい場合は、注文IDの重複を除くなど、集計の単位を指定する必要があります。
集計関数とGROUP BY、自動JOIN、結果のネスト、列名のスキーマ照合は今回の対象外です。
