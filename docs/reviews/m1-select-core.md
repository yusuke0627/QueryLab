# M1 SELECTコア レビュー資料

## 対象と学習目標

対象は共通Query Model、宣言的コンストラクタ、構造検証、SQLite SQL生成、Goソース生成です。
SQLite実行API、スキーマ照合、JOIN、MyGo GUI、SQL/Goの取り込みは未実装です。

Goでは構造体と独自型、スライスとポインタ、ジェネリクス、エラー処理、JSON、
標準ライブラリによるソース整形とテストを学びます。
アルゴリズムでは式ツリーの走査、検証と生成の分離、括弧による構造の維持、
プレースホルダーと引数の対応、生成結果の等価性を学びます。

## 設計判断と代替案

| 採用した方法 | 理由 | 代替案とトレードオフ |
| --- | --- | --- |
| 宣言的な構造体 | GUIとGoが同じモデルを使え、JSONに保存できる | fluent APIは記述しやすい一方、別途共有モデルと状態管理が必要になる |
| 種別を持つ`Expr` / `Scalar` | 保存・検証・生成を明示的に追える | interfaceでノードを分けると型ごとの操作を分離できるが、JSONの復元方法が必要になる |
| 生成前の共通検証 | SQLとGoで不正入力の扱いをそろえる | 生成中の検査にまとめると走査回数は減るが、診断が生成器ごとに分散する |
| スカラーの種別と`int64` | JSONを往復しても整数や真偽値の型を維持する | `any`でJSONを復元すると数値の型を別途管理する必要がある |
| 再帰的な式生成 | ノードとコードの対応が読みやすい | 明示的なスタックや共通バッファはコピーを減らせるが、制御が複雑になる |
| NULL判定ノードを明示 | `= NULL`とNULL判定の取り違えを早く発見できる | 自動で書き換える方式は簡潔だが、入力の意味を暗黙に変更する |

種別付き構造体は、不正なフィールドの組み合わせをGoの型だけでは排除できません。
そのため`Validate`を生成器の共通の入口とし、不要なフィールドも検査しています。
コンストラクタの存在だけでモデルが常に正しいとは見なしません。

## アルゴリズムと処理例

1. `Validate`がSELECT全体を調べ、各式を深さ優先で検証する。
2. SQL生成器が投影、FROM、WHERE、ORDER BY、LIMIT、OFFSETの順に出力する。
3. 式の生成では子を左から右へたどる。値に達したら`?`を出力し、同じ順に引数を追加する。
4. 二項式と論理式を括弧で囲み、ツリーのグループを維持する。
5. Go生成器は同じ検証済みモデルから構造体とコンストラクタ呼び出しを出力し、整形する。

実行例のWHEREは次の木になります。

```text
And
├── Compare (=)
│   ├── Ref(u, active)
│   └── Bool(true)
└── IsNull
    └── Ref(u, deleted_at)
```

WHEREだけのSQLは`(("u"."active" = ?) AND ("u"."deleted_at" IS NULL))`です。
`Bool(true)`で最初の引数が追加され、`IsNull`は値をバインドしません。
実行例ではその後のLIMITで`int64(20)`が追加され、全体の引数は`[]any{true, int64(20)}`になります。

## 正しさを支える条件

- 値のバインド順とSQL中の`?`の出現順が一致する。
- 値をSQL文字列に埋め込まず、識別子は引用し、演算子は許可したものだけを使う。
- 生成器は入力モデルを変更しない。モデルが検証エラーなら部分的なSQLを返さない。
- 式の子の順序と括弧を維持する。
- `nil`のLIMITと0のLIMITを区別する。OFFSET単独は`LIMIT -1`を補う。
- スカラーの種別と値をJSONと生成Goを通して維持する。

モデル内のポインタやスライスを他の処理が同時に変更する利用は対象外です。
`Select`や`Expr`を値としてコピーしても、参照先を含む深い不変性は得られません。

## 計算量の分析

以下は実装からの分析であり、ベンチマークの実測値ではありません。
Nをモデル要素数、Dを式の最大深さ、Lを生成する文字列の総長、Pを引数数とします。

- 検証の成功時は各要素を訪問するため、文字列の検査を除いてO(N)です。再帰スタックはO(D)です。
- 識別子と文字列値には長さに比例する検査も行います。
- SQLの値追加は合計で償却O(P)、保持する引数はO(P)です。
- 式生成は子の文字列を親で結合し直します。各部分のコピーが祖先で繰り返されるため、
  時間の上界はO(D × L)で、単純にO(N)とは言えません。Goの式生成にも同じ性質があります。
- SQL出力自体はO(L)の領域、式走査はO(D)のスタックを必要とします。中間文字列も割り当てます。
  Go生成では、これに`go/format`の解析・整形の処理と割り当てが加わります。

現在の深さ上限は128です。幅や総ノード数には上限がなく、入力全体の資源上限は未整備です。
共通バッファへの直接出力などの最適化は、正しさのテストと測定を用意してから比較します。

## 制約とレビューで確認したいこと

スキーマ照合、JOIN、BLOB、集約、GUI、SQL/Go取り込みは後続です。
JSONは未バージョン化で、完全な不変性や同時編集への保証はありません。
生成器内の`panic`は検証済みの種別だけが届く前提です。種別追加時に検証器と両生成器を
同時に更新する必要があり、Goの型検査だけで分岐漏れを検出できる設計ではありません。

- なぜ値と識別子を別の方法で出力するのか。
- 子の走査順を変えると、どのテストで引数の不一致を発見できるか。
- 値コピーと参照の共有をどう区別し、GUIの編集では何を追加する必要があるか。
- 種別を一つ追加するとき、どの検証・生成・テスト・文書を変更するか。
- 深さ制限では防げない入力を挙げ、その制限をどこで扱うべきか。
- Go生成の往復テストと、未実装のGo取り込みは何が違うか。

理解確認には[学習計画のM1演習](../learning-plan.md#m1の演習)も使用してください。
