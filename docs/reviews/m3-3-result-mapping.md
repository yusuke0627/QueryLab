# M3-3 JOINの結果を親と子にまとめる

## なぜ必要か

注文1に明細が2件あると、JOINの結果には注文1が2行出ます。
画面で「注文1の下に明細を2件並べたい」ときは、検索が終わったあと、Goで行をまとめます。
`execution.Execute` の結果は今までどおり平坦で、SQLも変わりません。

| 注文ID | 明細ID | 商品 |
| --- | --- | --- |
| 1 | 3 | apple |
| 1 | 4 | apple |
| 2 | NULL | NULL |

この3行を、注文1には明細3・4、注文2には明細なし、という2グループにします。
同じ商品名でも、明細IDが違うので2件とも残ります。

```go
groups, err := resultmap.Nest(flat, resultmap.Spec{
    Parent: resultmap.Selection{Key: []int{0}, Values: []int{0}},
    Child: resultmap.Selection{Key: []int{1}, Values: []int{1, 2}},
    Cardinality: resultmap.OneToMany,
})
```

`Key` は「同じ親や子かを判断する列」、`Values` は「結果に残す列」です。
列番号は0から始まります。列名が両方 `id` でも位置で区別できます。
`OneToOne` は親ごとに子0件または1件を許し、異なる子が2件あればエラーにします。
子はどちらのモードでも `Children` のスライスで返ります。

## 読み順と設計

1. [型とNest](../../resultmap/group.go)で、入力・出力の形とエラーになる条件を確認します。
2. 同ファイルの `rowKey` で、複合キーと文字列・整数を区別する仕組みを読みます。
3. [テスト](../../resultmap/group_test.go)で、実SQLiteのJOIN結果と変換結果を比較します。

- 行を順に読み、Goの `map`（キーから値を探す表）で見たことのある親と子を探します。スライスには最初に出てきた順で入れます。
- 親の中で子キーが重複し、選んだ値も同じなら、一件にまとめます。同じキーなのに選んだ値が違う場合は、どちらかを黙って採用せずエラーにします。
- 子キーがすべてNULLなら子なしです。複合キーの一部だけがNULLならエラーです。親キーにNULLは使えません。
- キーは `int64` と `string` に限定し、Goで完全一致を比較します。SQLiteの照合順序や型変換は再現しません。
  文字列を単に区切り文字で連結する案では衝突し得るため、型と長さを付けて区別します。
- 外部キーから結果列を推測する案は採らず、ユーザーが列位置を指定します。JOINが直接返す行と、画面に合わせたまとめ方を別にできます。

入力行数をRとすると、列数・値のサイズを固定した場合、mapの検索を使うため平均O(R)です。
実際の処理量にはキーの長さや選択した値の比較・BLOBコピーのコストも加わります。
出力と検索表は見つかった親・子に比例します。性能測定はしていません。

## 制約・確認方法

1段の親子関係だけを扱います。再帰的なネスト、結果列の推測、自動JOIN、SQLでの集計は対象外です。
`Truncated` が真なら、子が途中で欠け得るため拒否します。SQLの `LIMIT` や `WHERE` が省いた行は検出できず、渡された結果内だけでまとめます。
親や子を希望の順で表示したい場合は、SQL側で `ORDER BY` を指定します。

```sh
CGO_ENABLED=1 go test ./resultmap -count=1
CGO_ENABLED=1 go test ./...
CGO_ENABLED=1 go vet ./...
```

実SQLiteで同名列、同じ商品名でも別IDの明細、子なしのLEFT JOIN、1対1と1対多を確認します。
追加テストで複合キーの衝突防止、重複と順序、BLOBのコピー、エラー時に部分結果を返さないことを確認します。
macOS arm64で、Go 1.23.12の対象・全体テストとGo 1.25.7の静的チェックが成功しました。
