# M2-2 SQLiteスキーマ取得のレビュー

## 目的と読み順

検索結果ではなく「DBにどんなテーブルや列があるか」を調べます。
たとえば `users.id` が整数として宣言された主キーだと分かりますが、値の `1` は読みません。

1. [実行例](../../examples/schema/main.go)で、DBを開く → 定義を取得する → JSONにする流れを追う。
2. [結果の型](../../schema/model.go)で、テーブルの中に列・外部キー・索引が入る構造を見る。
3. [Read](../../schema/read.go)で、定義の一覧を読み、テーブルごとの詳細を追加する流れを追う。
4. [実SQLiteテスト](../../schema/read_test.go)で、入力のCREATE文と期待する結果を比較する。

## 実装の判断

- `schema.Read(ctx, db)`は、DBを借りて定義を読む関数です。DBは閉じず、内部で開いたRowsとトランザクションを片付けます。
- `sqlite_schema`と[SQLiteのPRAGMA](https://www.sqlite.org/pragma.html#pragma_table_list)を利用します。CREATE文を文字列として解析する案より、SQLite自身が返す構造化情報を使うほうが、引用符や複合キーの扱いを再実装せずに済みます。
- 一覧と詳細を別々に読みますが、一つのトランザクションにまとめて、同じ時点の定義を取得します。名前はSQLに連結せず、引数として渡します。途中で失敗したら部分結果は返しません。
- `PrimaryKeyOrdinal`は列の表示順とは別で、0は主キーではなく、1以上は主キー内での順番です。外部キーは同じIDの列の組を順番にまとめます。
- `DefaultSQL == nil`は既定値の指定なしで、`"NULL"`は明示的な `DEFAULT NULL` です。外部キーの参照先列が `nil` なら、DDLで参照先列が省略されています。
- `DeclaredType`は定義上の型で、行の値の型ではありません。`NotNull`はSQLiteが報告するフラグで、これだけで実際にNULLを許すかは判断しません。

テーブルと索引は名前順、列とキーの構成要素はSQLiteが返す位置の順です。
一覧取得を1回、テーブルごとの詳細を最大3回、索引ごとの詳細を1回問い合わせます。
Go側は取得した定義の行数に比例して情報を収集します。SQLite内部のソートやカタログ走査を含む性能は測定していません。

## 対象外・制約

- `main`のユーザーテーブル・ビュー・仮想テーブルが対象です。TEMP、添付DB、SQLite内部テーブル、仮想テーブルの補助テーブルは除きます。
- 生成列・隠し列は `HiddenCode` で区別します。索引はキー部分を返し、式の項は `ColumnID == -2` として保持します。式本文と部分索引のWHERE本文は復元しません。
- 定義が壊れたビューなど、SQLiteが列情報を取得できない場合は全体をエラーにします。JOINの自動生成やクエリのスキーマ照合はまだ行いません。

## 再現と理解の確認

```sh
CGO_ENABLED=1 go test ./schema -count=1
CGO_ENABLED=1 go run ./examples/schema /path/to/users.db
```

テストは実SQLiteで、引用符を含む名前、TEMPの同名テーブル、複合主キー・外部キー、生成列、部分索引と式索引、
空のDB、キャンセル、失敗後の接続再利用を確認します。実行例は[READMEのデモDB](../../README.md#sqliteで実行する)でも試せます。
